# OpsAgent: Write-up

**Author:** Shubh Bohra · **Track:** Agentic AI Engineer Intern (AI Automation Engineer opportunity) · **Assessment:** Option 3, Autonomous Knowledge Execution Agent

## Domain, goal and data (paste into the form)

OpsAgent is an operations agent for ShopKart, a fictional Indian e-commerce store. An operator gives a goal in plain English (refund an order, cancel an order, restock items, handle a support ticket, or answer a policy question). The agent plans, retrieves in parallel from three internal sources, reasons, and handles conflicting or missing information. It explains each decision, asks for human approval on critical actions, executes, and writes an audit log, long-term memory, and a JSON/Markdown report. All data is synthetic and committed in the repo: 16 customers, 36 orders, 20 products, 5 policy documents, tickets and prior memory, all generated by `scripts/generate_seed.py`. The seed data deliberately contains a policy conflict (a 2026 30-day refund window vs. a 2024 15-day FAQ), a final-sale product that conflicts with the general policy, an ambiguous customer with three open orders, a repeat-refund customer, and a ticket with a prompt injection. Actions are simulated against the local database (emails go to an outbox table). The demo date is fixed at 2026-09-27 so results are reproducible.

## Design decisions

- **LangGraph state machine** (DEC-002): explicit nodes for plan, retrieve, reason, clarify, validate, approve, execute, respond and save memory. `interrupt()` plus a SQLite checkpointer gives real human-in-the-loop pauses that survive restarts.
- **The LLM decides, code guards** (DEC-004): the LLM chooses retrievals, resolves conflicts, picks actions and writes explanations. Deterministic code enforces the allow-list, schemas, cited-evidence checks, business invariants, risk tiers and approvals. This follows the "no predefined rules" constraint without trusting the model with money.
- **Structured outputs instead of a free ReAct loop** (DEC-005): each proposed action is visible, validated and approvable before any side effect, and retrievals can run in parallel. It also means only 2 to 3 LLM calls per run.
- **Parallelism with safety** (DEC-010): a scheduler groups actions by dependency level and never runs two actions on the same entity at once. Each action is one transaction and is idempotent per run.
- **Money in paise** (DEC-018): stored as integers, shown as 2-decimal rupees, with no floats anywhere, so ₹5,000.00 is auto-approved and ₹5,000.01 is not.
- **Self-correction everywhere**: transport retries with rate-limit-aware backoff, a structured-output repair round, a validation repair round with the validator's feedback, and tool and DB retries. `--inject-failure` demonstrates each path.
- **Provider-agnostic LLM layer** (DEC-003): Groq GPT-OSS 120B by default, Gemini by one env change.

## Evaluation

There are 61 offline tests with a scripted fake LLM that prove the guarantees hold whatever the model says: a prompt injection cannot bypass approval, rejected actions skip their dependents, and there are no double writes on retry. `opsagent eval` runs 10 live scenarios (approval, conflicts, clarification, decimals, parallel restock, out-of-scope, injection, memory, precondition failure) and saves the pass rate to `eval/results/`. Latest live run: **10/10 passed** with Groq `openai/gpt-oss-120b`. The first live run scored 7/10; the failures (placeholder lookups, a missed policy-version conflict, ignored customer history) were fixed through retrieval and prompt changes, not by hard-coding answers (DEC-023).

## Limitations

- Simulated actions only; no auth, and one operator both requests and approves.
- Free-tier LLM rate limits can slow long eval runs; answer quality depends on the model.
- Memory is recency-based per customer, not semantic.
- The policy index falls back to a simple offline embedding when the ONNX model cannot be downloaded.

## With more time

- Separate requester and approver roles, and approval via Slack or email.
- A FastAPI service with a proper web UI and streaming.
- Semantic memory, a critic pass before execution, and a larger labelled eval set tracked in CI.
- Real integrations (payment refunds, SMTP) behind the same action registry.
